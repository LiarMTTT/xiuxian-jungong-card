## 0. 本轮问题

用户问：继续头脑风暴，色情设定会不会导致 git 仓库爆炸？

结论先行：**几乎不会因为“仓库里有色情设定”就把 git 撑爆。**  
当前这个公开库打包大约 67KB，全是 Markdown 和少量预览前端。真正会爆的是另外三件事：二进制资产、把黄文例文集当成正典无限追加，以及把露骨正文提交到当前这个 **公开 GitHub 仓库** 后触发政策、检索和 Pages 事故。后一种不是磁盘爆炸，是仓库被炸号 / 被下架的爆炸。

## 1. 先把“爆炸”拆开

| 爆炸类型 | 会不会因为色情设定发生 | 实际原因 |
|---|---|---|
| Git 体积爆炸 | 纯文本机制几乎不会 | 角色卡 PNG、立绘、语音、base64 内嵌图、地图瓦片才会 |
| 世界书 / 上下文爆炸 | 会，如果写法错 | 把每对关系、每种交合、每个派系都写成常驻条目 |
| GitHub 托管爆炸 | 公开库 + 露骨正文时会 | GitHub 可接受使用政策禁止以唤起色情反应为主要目的的露骨性描写，含文字 |
| 设计组合爆炸 | 会，如果当内容农场 | 基调 × 合欢宗派系 × 尸魁个体 × 动作清单互相乘 |

已冻结的协作原则已经挡过第四类：成人机制可以是尸魁供养、关系和世界设定的重要部分，但不让无关系统被性内容淹没。合欢宗也不许被压成单薄色情宗门。

## 2. 体积：文本几乎无害，角色卡和媒体才有害

当前基线：

- `git count-objects` 打包约 67KB，对象 51 个。  
- `.gitignore` 已经忽略 `*.png`。这很关键：SillyTavern 角色卡常见形态就是带内嵌 JSON 的 PNG，一张立绘卡动辄数 MB；若再把多张 CG、语音、base64 头像写进 JSON 并提交，仓库会按提交次数线性膨胀，而且 Git 对已提交二进制几乎不能有效差分。  
- 地图瓦片已经证明过这件事：正典不进 git，Pages 构建时再拉取。成人向媒体更应该沿用同一纪律。

经验量级（建议，非测量正典）：

- 机制、因果、派系、供养规则：就算写到两万字，也只是普通 Markdown。  
- 官方例文、样章、逐角色床戏脚本：会把设计库变成网文章节站，体积未必先爆，维护和检索会先爆。  
- 一张未忽略的 8MB 角色卡 PNG 进 git，比一整本合欢宗白皮书更伤仓库。

因此：**色情设定本身不是体积炸弹；把成品卡、立绘和例文集当源码提交才是。**

## 3. 上下文：这才是酒馆卡更常见的爆炸

SillyTavern / MVU 的真实瓶颈通常不是 git，而是提示词。如果把下列东西全部做成常驻世界书：

- 合欢宗每个派系的房中术细节；  
- 每位尸魁的性癖、适配、体位偏好；  
- 阳精、双修、采补的全套动作说明书；  
- 每个可攻略角色的样章；

主持模型会在打铁、赶路、谈外交时也被性内容淹没。这直接违反已冻结的文风边界。

建议沿用已经冻结的 **情报五层** 思路，而不是另发明一套黄色目录：

1. **公开机制**：阳精是食物和可炼化灵力；交合可促进供养，但不是唯一成长；活炼、危险投喂、婚约与契约有代价。  
2. **势力 / 地点层**：合欢宗、特定坊市、双修洞府、局部伦理基调。只在进入或打交道时触发。  
3. **关系层**：以沫、龙曦或动态角色的亲密状态。只在关系已经成立、且当前场景需要时触发。  
4. **例文 / 高露骨层**：怎么写、写多露骨。默认不进基础运行包，也不进公开 git。

深层秘密不能只靠前端隐藏；成人例文同样不能只靠“文件名写了 NSFW”。不进基础包，按条件交付。

## 4. 托管：当前仓库是公开的，这比体积更危险

`LiarMTTT/xiuxian-jungong-card` 当前 **public**。GitHub 可接受使用政策写明：不欢迎主要以唤起色情或震惊反应为目的的性暗示内容；禁止色情内容，以及性行为的图形化描绘，范围包括照片、视频、动画、绘图、计算机生成图像 **和文字**。艺术、教育、历史、新闻语境可能被允许，但 GitHub 仍可限制可见性或要求 opt-in。该政策覆盖仓库、Issues、Pages 等全部服务。

对本项目的含义（建议，不是法律意见）：

- **机制白皮书**（阳精是资源、合欢宗是情报与婚契网络、交合有因果）更接近世界规则，相对安全。  
- **露骨性行为正文、床戏样章、色情绘图 / CG** 更接近政策禁止项。  
- **GitHub Pages** 已经在发地图预览。地图必须继续保持非色情；不要把成人包、立绘或样章挂到 Pages。  
- 先提交再改私有，历史里的对象还在。公开期间被克隆、被搜索引擎收录后，清理成本远高于一开始就分层。  
- 云端 agent、CI、Copilot 类工具对露骨正文更敏感。设计库被写成黄文站后，后续续接会变脆。

公开仓库里保留“这个世界存在情欲、双修和尸魁供养”不等于公开仓库里保存色情作品。

## 5. 建议的仓库分层（未拍板）

```text
公开 git（本仓库）
├── 机制：阳精、供养、驯化与正规契约的差异、危险资源
├── 势力：合欢宗总纲、派系理念、婚契 / 情报 / 艺术，不写成单薄色情宗门
├── 可选基调槽位：允许未来增加“情欲浓度 / 礼法”类世界基调，正文待拍板
└── 不提交：露骨例文、CG、语音、角色卡 PNG、base64 媒体

私有成人包（候选，待选一种）
├── 独立 private 仓库
├── 本仓库 gitignore 本地目录
├── 工坊可选包（只进候选世界书，不直接写 MVU）
└── 先不建包，只在公开库写规则，例文完全不入库
```

运行时建议：

- 成人机制属于世界物理，已经冻结，不因为“怕 git 爆炸”删掉。  
- 高露骨描写属于可选包或局部基调，按地点、关系、玩家行动触发。  
- 工坊成人包遵守既有工坊边界：可下载、可拆解、不能直接改正式 MVU。  
- 官方不需要为每种玩法预写样章。玩家和模型按已成立关系与因果现场生成即可。

不建议做的事：

- 为了“完整”把动作清单、性癖图鉴、全员床戏脚本写进 `plan.md`。  
- 把角色卡 PNG 当版本管理对象。  
- 用 GitHub Pages 做成人图库或样章站。  
- 因为托管风险，反过来把已冻结的阳精、合欢宗、真龙婚约从世界上抹掉。
